# TrustLens AI — Machine Learning Documentation

This document describes the models, datasets, training gates, inference behaviour and honest limitations that are present in this repository. It is based on the checked-in artifacts and source code; it does not assume a live deployment, additional labelled data, or any external credentials. The authoritative runtime manifest is `backend/models/model_manifest.json`.

## Dataset provenance

### Real job-description corpus: EMSCAD

The job models are trained from `backend/data/raw/emscad_v1.csv`. The manifest records the training machine's absolute path, but the repository-relative path above is the file present in this working tree.

| Property | Recorded value |
| --- | --- |
| Dataset name | `emscad_v1` |
| Origin | University of the Aegean EMSCAD corpus, CC0-origin Kaggle mirror |
| License note | CC0-origin; redistribution and modification permitted |
| Raw rows | `17,880` (verified directly from the CSV in this working tree) |
| Raw label values | `f` = `17,014`, `t` = `866` |
| Invalid labels dropped | `0` |
| Text shorter than 20 characters dropped | `0` |
| Duplicate normalized texts removed | `2,180` |
| Rows after cleaning | `15,700` |
| Class counts after cleaning | `0` (legitimate) = `14,993`, `1` (fraudulent) = `707` |
| `real_world_data` / `production_grade` in manifest | `true` / `true` |

The `production_grade` field is a provenance marker in the manifest, not a guarantee of production accuracy. EMSCAD is a job-posting benchmark corpus, not a stream of live user reports.

`load_emscad_dataset()` accepts `f`/`t` plus common boolean variants, requires a `fraudulent` label column, requires at least 20 rows per class, and combines the available text columns `title`, `company_profile`, `description`, `requirements` and `benefits`. Text is normalized before de-duplication, so postings that are identical after that normalization cannot appear in both training and test splits; merely near-identical postings can still remain.

### Synthetic recruitment-message corpus

`backend/app/ml/datasets/synthetic_messages.py` contains hand-authored email/SMS/WhatsApp-style examples. It is explicitly marked **not real-world**, **not production-grade** and for internal evaluation only. Ambiguous and incomplete examples are present for documentation and fallback testing but are excluded from supervised training by default.

The `message_tfidf_logreg` model in the manifest uses this corpus. Its metrics must always be labelled synthetic benchmarks and must never be reported as production KPIs.

### Anomaly feature provenance

The anomaly models are trained on the same cleaned EMSCAD rows, using a fixed 24-feature vector from `backend/app/ml/features.py`. Text-derived signals (length, urgency terms, payment terms, personal-data terms, capital ratio and similar) come from the postings. Metadata signals such as missing salary, missing logo, missing questions and telecommuting come from EMSCAD columns.

Contextual signals such as domain age, reputation, company age, scam reports and sender-domain mismatch are **absent from EMSCAD** and are set to neutral zeroes during training. The manifest records that runtime values from upstream lookups are unvalidated for those models.

## Preprocessing and splitting

### Text normalisation

`normalize_text()` in `backend/app/ml/features.py` is shared by training and inference to avoid train/serve skew. It:

1. Applies Unicode NFKC normalization.
2. Unescapes HTML entities and strips HTML tags.
3. Replaces URLs, e-mail addresses, phone numbers and digit runs with the sentinel tokens `URLTOKEN`, `EMAILTOKEN`, `PHONETOKEN` and `NUMTOKEN`.
4. Lowercases text, removes punctuation and collapses whitespace.

The intent is to let models learn the presence of contact channels and numeric patterns rather than memorise specific addresses or numbers.

### Vectorisation and classifiers

`_text_pipeline()` builds a `scikit-learn` pipeline whose TF-IDF vectorizer is fitted on the training split only:

| Setting | Value |
| --- | --- |
| N-grams | `(1, 2)` |
| `min_df` | `2` for the active EMSCAD run; `1` when the training split has fewer than 200 rows or for the message model |
| `max_df` | `0.95` |
| `max_features` | `30,000` |
| `sublinear_tf` | `True` |
| `strip_accents` | `unicode` |
| `lowercase` | `True` |

Classifiers:

| Family | Classifier configuration |
| --- | --- |
| `job_tfidf_logreg` | `LogisticRegression(max_iter=2000, class_weight="balanced", C=1.0)` |
| `job_tfidf_linearsvc` | `LinearSVC(C=0.5, class_weight="balanced", max_iter=5000)` |
| `message_tfidf_logreg` | Same logistic-regression pipeline as the job model, with `min_df=1` |

For LinearSVC, scoring code applies a sigmoid to the clipped decision margin and flags the result as a ranking score, not a calibrated probability. This artifact is approved in the manifest but is not currently called by `TextPredictor.predict_job()`.

### Splits and thresholds

`stratified_split()` uses a fixed `RANDOM_SEED = 42` and a 60% train / 20% validation / 20% test split. For the current cleaned corpus this is approximately:

| Split | Rows |
| --- | ---: |
| Train | `9,420` |
| Validation | `3,140` |
| Test | `3,140` |

`select_threshold()` in `backend/app/ml/evaluation/metrics.py` chooses thresholds on the **validation split only**. It considers observed scores and a grid from `0.05` to `0.95`, keeps candidates with precision at least `0.35` and false-negative rate at most `0.30`, then minimises FNR with F1 as a tie-break. If no candidate qualifies, it maximises F1 with FNR as a tie-break. Degenerate single-class splits return `0.5`.

All reported metrics come from the untouched test split via `binary_metrics()`.

## Model selection and approval gates

Training is per family rather than a champion/challenger tournament. There is no code that automatically selects one winner across families and no human sign-off step. A family is written as `approved: true` only if every applicable gate in `_approval()` passes.

Common hard blockers:

- `provenance.real_world_data` is not `true` — synthetic-only models can never be promoted.
- ROC-AUC below the family minimum.
- Recall below the family minimum.
- False-negative rate above the family maximum.
- Precision below `0.15`.
- False-positive rate above `0.40`.
- Test support below `100`.
- Degenerate single-class evaluation split.

Family-specific ranking/recall gates:

| Family | Minimum ROC-AUC | Minimum recall | Maximum FNR | Outcome |
| --- | ---: | ---: | ---: | --- |
| `job_tfidf_logreg` | `0.70` | `0.35` | `0.70` | Approved |
| `job_tfidf_linearsvc` | `0.70` | `0.35` | `0.70` | Approved |
| `message_tfidf_logreg` | `0.70` | `0.35` | `0.70` | Rejected: synthetic provenance; support is also only `8` |
| `anomaly_iforest` | `0.60` | `0.20` | `0.85` | Rejected: recall `0.1773` is below `0.20` |
| `anomaly_supervised` | `0.75` | `0.40` | `0.70` | Rejected: recall `0.3404` is below `0.40` |

Rejected artifacts are still written to `MODEL_DIR` with `approved: false` and `active: false` for audit. `TextPredictor` filters manifest candidates to `approved is True`, so rejected artifacts are not loaded at runtime.

## Inference flow

### Runtime loading

`TextPredictor` in `backend/app/ml/inference/predictor.py`:

1. Reads `MODEL_DIR/model_manifest.json`.
2. For a requested family, keeps manifest entries with `approved is True`, prefers entries with `active is True`, and loads the referenced `joblib` bundle.
3. Verifies that the bundle payload itself also has `approved: true`.
4. Caches successfully loaded artifacts for the lifetime of the predictor instance.
5. Returns a deterministic rule fallback if the manifest is missing/unreadable, no approved entry exists, the artifact fails to load, or inference raises.

The fallback model names end in `_rule_fallback`, the version is `rule-fallback-1.0`, and limitations explicitly say that no trained model was used and the rule scores are unvalidated heuristics.

### Analysis orchestration

`AnalysisService.run()` in `backend/app/services/analysis_service.py` performs the end-to-end flow:

1. Check plan quota and optional idempotency by `client_request_id`.
2. Read the user's `consent_external_lookups` flag from the request.
3. Parse documents without executing file content and extract entities.
4. Call model predictors:
   - `job`, `document`, `monitoring`: `predict_job(text)` → job text model or `job_text_rule_fallback`.
   - `message`, `job`, `document`: `predict_message(text, channel)` → message model or `message_text_rule_fallback` (currently fallback because the message model is rejected).
   - Structured anomaly features: `predict_anomaly(...)` → `anomaly_iforest`, then `anomaly_supervised`, otherwise `anomaly_rule_fallback` (currently fallback because both anomaly models are rejected).
5. Apply consent-gated external URL/domain/company lookups.
6. Build rule indicators, de-duplicate them by name and persist them.
7. Call `score_risk()` with model predictions, indicators and available intelligence.
8. Persist the completed result, consume one scan, and notify on scores of at least 60 when notification delivery is configured.

Short normalized inputs are handled explicitly. With an approved model, fewer than three normalized words returns `inconclusive`; in fallback mode, fewer than four words returns `inconclusive`.

### Confidence, probability and risk score

- `fraud_probability` is a legacy field name for the model's fraud-oriented score used by the risk engine. For logistic regression it comes from `predict_proba`; for LinearSVC and several anomaly paths it is a sigmoid-mapped decision score. Present it to users as an **uncalibrated model risk score**, never as a calibrated fraud probability.
- `confidence` is a margin/evidence-strength indicator computed from distance to `0.5` and capped at `0.95`. It is **not** a calibrated probability and is **not** used as the risk score.
- `score_risk()` in `backend/app/core/risk_engine.py` combines the model's uncalibrated risk score with message, domain, company, history, brand and threat indicators. It discounts fallbacks (`0.45` trust), inconclusive predictions and synthetic claims, takes the strongest non-overlapping sub-signal inside each category, then normalizes weights over available signal categories only.
- Default weights from `Settings.risk_weights` follow the specification split: `content` `0.30`, `url` `0.25`, `brand` `0.25`, `threat` `0.10`, `community` `0.10`, normalized at runtime. `RISK_WEIGHT_*` environment variables override them; the legacy six-weight variables are ignored.
- Risk bands are `0–19 Low observed risk`, `20–39 Limited warning signals`, `40–59 Moderate risk`, `60–79 High risk`, and `80–100 Critical risk indicators`, configurable through `RISK_BAND_*_MAX`. Verified indicators and confirmed malicious reputation apply explicit boosts. Low coverage sets `inconclusive=True` and suppresses reassuring language. An empty threat/brand/history lookup remains `unavailable_signals` rather than becoming a clean zero.

## Explainability

Each prediction returns `model_name`, `model_version`, `prediction`, `fraud_probability`, `confidence`, `contributing_features` and `limitations`.

| Source | Explanation mechanism |
| --- | --- |
| Approved text models | Top five signed TF-IDF × linear-coefficient terms, with `increases_risk` / `decreases_risk` direction and a human-readable description |
| Approved anomaly models | Top five features by absolute `value × model weight`, with direction from the sign of the product |
| Rule fallbacks | Explicit lexicon or feature-hit descriptions such as “Rule fallback matched high-risk phrase …” |
| Risk assessment | `evidence_summary`, `recommended_actions`, `confidence`, `uncertainty`, `component_scores`, `signal_weights`, `unavailable_signals`, `data_coverage`, `weights_version`, `inconclusive` and a category summary |
| Source provenance | Timestamped `evidence_sources` records with honest statuses and engine detail |

These are feature attributions and heuristics. They show what moved a score in this implementation; they are not causal explanations, proof of fraud, or independent verification.

## Retraining

The CLI entrypoint is `backend/scripts/train_models.py`. From the repository root:

```powershell
.\.venv\Scripts\python.exe backend/scripts/train_models.py --data-dir backend/data --model-dir backend/models
```

```bash
python backend/scripts/train_models.py --data-dir backend/data --model-dir backend/models
```

Options:

| Flag | Behaviour |
| --- | --- |
| `--data-dir` | Dataset directory; the loader looks for `raw/emscad_v1.csv`. |
| `--model-dir` | Destination for `joblib` artifacts, `*.meta.json` and `model_manifest.json`. |
| `--log-level` | Python logging level; defaults to `INFO`. |

If paths are omitted, `Settings.data_dir` and `Settings.model_dir` are used. The CLI resolves relative settings paths against `backend/` when they do not already exist. Without a root `.env`, the settings defaults are `./models` and `./data`, so explicit paths are recommended when running locally.

`train_all()` then cleans the data, trains every family, applies the approval gates, writes versioned artifacts and metadata, rewrites `model_manifest.json`, and prints a JSON summary. Rejected artifacts remain on disk for audit, but the new manifest controls what inference considers approved. The CLI does not pass a `Repositories` instance, so it does not register approved models in the database registry.

A retrain does not hot-reload a running API. `AnalysisService` caches its predictor, and Docker images bake model artifacts into `/app/models`. Restart/redeploy the API and verify the manifest version before treating a retrained model as live.

## Monitoring and drift recommendations

These are recommendations only; this repository does not implement a production model-monitoring or drift-detection pipeline.

- Record the manifest `training_version`, `model_name`, `model_version`, prediction, fraud probability, fallback flag, latency, analysis type, language if known, risk score and data coverage with each served prediction.
- Track the distribution of fraud probabilities and score bands over time; alert on sudden shifts or a collapsing score variance.
- Track fallback rate by family. A non-zero or rising message/anomaly fallback rate is expected today; an increase in job-text fallback indicates a manifest or artifact problem.
- Segment metrics and scores by channel, language, source and length. EMSCAD is English job descriptions; performance on other channels is unvalidated.
- Use `POST /api/v1/reports/feedback` labels as a review queue, not as automatic ground truth. Feedback is stored as `pending_review`.
- Re-evaluate precision, recall, FNR and FPR on genuinely labelled held-out data before retraining or changing thresholds. Do not tune thresholds on test data.
- Compare new manifest runs against the current held-out baseline and require review of provenance, support, confusion matrix and rejection reasons before promotion.
- Monitor operational health: request errors, p95 latency, quota refusals, webhook failures, database availability and queue depth. Existing `/health` checks cover HTTP readiness and datastore pings, not model quality or queue depth.

## Honest limitations

- Text-only models do not independently verify the employer, domain or sender.
- The approved job models are trained on an English-language job-posting corpus. Performance on other languages, regions and message channels is unvalidated.
- There is no real labelled recruitment-message corpus in this repository. The message model is synthetic and rejected; runtime uses rule-based fallback.
- The anomaly models are rejected. Contextual features needed for them are absent from EMSCAD and were neutral zeroes in training; runtime lookup values are unvalidated for those models.
- High ROC-AUC coexists with moderate precision for the approved job models. False positives are possible and expected; a positive score warrants review, not an accusation.
- `fraud_probability`, LinearSVC sigmoid output, anomaly sigmoid output and `confidence` are not calibrated probabilities.
- The risk score is an explainable evidence blend, not a model output and not a statement of ground truth.
- `job_tfidf_linearsvc` is approved in the manifest but is not currently called by inference.
- No fairness, bias, adversarial-robustness, multilingual, calibration or external-validation study is present.
- Feature attributions and rule hits are not causal explanations.
- Rejected metrics and synthetic-corpus metrics are audit information, not product performance claims.
- Retraining changes files but does not automatically update a running process or container image.

## Prohibited claims

Do not state or imply any of the following:

- “The system detects all scams” or “guarantees fraud detection”.
- “99% accurate”, “near-perfect” or any headline accuracy derived only from ROC-AUC.
- That synthetic message metrics are production KPIs.
- That message or anomaly ML models are active; they are rejected and runtime uses rule fallbacks.
- That `job_tfidf_linearsvc` is used by current inference.
- That `confidence`, `fraud_probability` or a sigmoid-mapped margin is a calibrated probability.
- That the risk score is a model confidence value or a calibrated probability of fraud.
- That a low score proves a posting, employer or sender is legitimate. Low coverage is marked inconclusive.
- That the text model independently verifies employers, domains or senders.
- That the platform supports languages or channels beyond what has been evaluated. This documentation does not claim validated non-English performance.
- That the system is certified, legally compliant, bias-free or a substitute for human review.
- That a retrained model is live before the API is restarted/redeployed and the manifest version is verified.
